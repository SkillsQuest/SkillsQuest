# `skilltree/1` 文档格式

一份技能树是一份自足的 JSON 文档：手机上点几下能产出，高级玩家能手写，
程序能 Patch，任何人都能拿开源工具校验与渲染。

> 这份文档是中文的，字段名与示例 JSON 与语言无关。
> **代码里没有注释，规范只在这一份文档里**：`src/skilltree` 是它的参考实现，
> 逐节对着读。规范之外的东西（宿主怎么存、怎么发奖励、界面怎么画）不在这里。

## 3.1 分层模型

| 层 | 内容 | 谁消费 | 可变性 |
| --- | --- | --- | --- |
| **L0 结构层** | `nodes` / `edges` / `gate` / `rules` / `res` / `awards.need` | 规则引擎（解锁、树内结算、成就判定） | 语义核心，向后兼容约束最严 |
| **L1 表现层** | `layout` / `theme` / 节点坐标 `x,y` / `meta` | 渲染器与列表页 | 可丢弃可重算；`meta` 是描述性数据，约束宽松 |
| **L2 扩展层** | 文档级与节点级 `ext` 容器 ＋ `requires` 能力声明 | 高级定制 | 未知 `ext` 键必须原样保留、不得报错 |

两条跨层的规矩：

- **布局只动坐标，不动语义。** 自动整理、换排布重排的是 `x,y`，一个 L0 字段都不碰。
- **引擎产出事件，宿主决定奖励。** 引擎负责四态、树内资源、等级、连带集合，以及
  「完成了一个 `kind=boss` 的节点」「跨过了成就线 `aw1`」这类**结算事件**。
  这些事件值多少钱是宿主策略，不属于可移植文档 —— 否则第三方宿主无从兑现。
  `awards[].gem` 留在文档里，但规范定义它为**宿主参考值**，不是引擎结算输出。

## 3.2 文档格式

```jsonc
{
  "spec": "skilltree/1",            // 必填。major 版本号在名字里
  "meta": {
    "name": "日语",
    "icon": "book",                  // 图标 key，非法值渲染端落 'dot'
    "accent": "#f0663f",
    "description": ""                // 可选
  },
  "layout": "flow",                  // flow | web | mind
  "nodes": [
    { "id": "a1", "title": "五十音", "icon": "abc", "x": 0, "y": 0,
      "kind": "boss",                // core | leaf | boss | 缺省
      "note": "",                    // 可选
      "gate": { "need": 1, "all": false, "cost": 2, "lv": 2,
                "when": { "gte": [{ "get": "attr.str" }, 14] } },  // 能力 cond/expr
      "maxRank": 1,                  // 能力 rank/alloc
      "ext": {} }                    // 节点级扩展容器（可选）
  ],
  "edges": [["a1", "a2"]],           // [前置, 后继]，有向
  "theme": { "shape": "circle", "edge": "solid", "bg": "dots", "arrows": false },
  "res":   { "name": "假名", "icon": "star" },
  "rules": { "daily": 6, "strict": false, "checkin": false },
  "attrs": [ { "key": "str", "name": "力量", "type": "number", "min": 1, "max": 20 } ],
  "awards": [ { "id": "aw1", "name": "开口", "icon": "medal", "need": 4, "gem": 3 } ],
  "requires": ["cond/expr", "attr/self"], // 能力声明，见 §3.6
  "ext": {}                          // 文档级扩展容器
}
```

**文档不含树的 id。** 树的身份属于存储层（数据库主键、文件名），可移植文档不携带；
节点 `id` 保留 —— 进度记录引用它。

**节点 id 规则**（多生产者协作的前提）：`[a-z0-9_-]{1,32}`，树内唯一。建议生产者
加前缀区分来源（编辑器 `n`、脚本自定），于是「这个节点哪来的」在文档里是自解释的。
后缀要足够长的随机段：「会话内计数器 ＋ 时间戳末几位」那种在多生产者下有现实碰撞
概率，而撞了之后整个变更会被唯一性校验拒掉。

字段语义（引擎实现必须一致的部分）：

| 规则 | 定义 |
| --- | --- |
| 节点四态 | `done` / `open` / `blocked`（前置够、cost 或 lv 或条件不够）/ `locked`（前置不够）。**blocked 与 locked 必须区分** |
| 前置数 | `rules.strict` 或 `gate.all` → 全部；否则 `gate.need ?? 1`；**求值时**再与实际入边数取 min（文档本身不改写，§3.3） |
| 求值输入 | 一个**状态对象** `{ ranks, facts?, nodes? }`。`ranks` 是「节点 id → 档位」，档位 1 就是布尔树里的「完成」；`facts` / `nodes` 是引擎自己算不出来的事实（要读时钟或读外部数据的） |
| 树内资源 | 纯派生：`earned(Σreward) − spent(Σ已完成节点的 gate.cost)`，无独立状态，撤销自动回吐 |
| 等级 | `floor(完成数 / 4) + 1`（v1 固定，参数化见 §3.6） |
| 树内奖励 | reward：boss 3 / core 2 / 其他 1。能量消耗同构（v1 固定） |
| `rules.daily` | 每用户时区日、每棵树的完成次数上限。规范定义语义，由宿主强制执行 |
| 连带取消 | 不动点迭代：去掉目标节点后反复剔除前置不再成立的已完成节点，直至收敛。返回集不含目标节点本身 |

### 3.2.1 条件与数据目录（能力 `cond/expr`）

`gate` 的四个字段是并列关系，表达不了「敏捷 ≥ 15」「选了 A 就不能选 B」
「（A 且 B）或（C 且 D）」。`gate.when` 是一条**可组合的条件**，十三个运算符：

- 组合：`all` / `any` / `not`
- 比较：`eq` / `ne` / `gt` / `gte` / `lt` / `lte`
- 集合：`in`（事实在这批值里）/ `has`（某节点的档位达到没有）
- 互斥：`oneOf`（这批节点里被选中的不超过一个）
- 取值：操作数里的 `get`

**不发明语言，也不依赖第三方的**：多个实现要零依赖且逐位一致，而通用表达式语言
（CEL 等）在每种宿主语言里都是一份独立实现 —— 那正是黄金测试集要防的漂移。
形状照 JsonLogic。

条件能读到的事实（**数据目录**）：

| 名字 | 谁算 | 含义 |
| --- | --- | --- |
| `node.rank` | 引擎 | 这个节点的档位 |
| `node.count` | 宿主 | 这个节点被完成过几次 |
| `node.at` | 宿主 | 最近一次完成的日期（`YYYY-MM-DD`） |
| `tree.done` / `tree.res` / `tree.level` / `tree.spent` | 引擎 | 已完成数、资源余量、等级、已花资源 |
| `tree.points` / `tree.used` / `tree.free` | 引擎 | 加点池总量、已投、剩余 |
| `tree.streak` | 宿主 | 这棵树的连续天数 |
| `tree.today` | 宿主 | 今天在这棵树上完成了几次 |
| `attr.<名字>` | 宿主 | 作者定义的属性（§3.2.3） |
| `tag.<名字>` | 宿主 | 节点或树上的标签 |

两条硬约束：

- **派生量由引擎现算，宿主传不进来。** 传得进来就多了一个可能算错的地方，
  而算错了不报错。
- **求值不读时钟。** 日期相关的事实由宿主按用户时区算好后放进状态对象。
  各实现各自取时间必然算出不同结果，而这种错不报错。

求值是**三值**的：缺事实是「不知道」，不是 0、不是报错。不知道一路传播到顶
（`not` 也不把它翻成成立），最后当条件不成立 —— 门宁可关着。

### 3.2.2 `ext` 的边界（L2）

三条，就这三条：

1. **键用反域名或短前缀**（如 `"sq.style"`）。平台留自己的前缀，作者用自己的。
2. **平台不解释任何 `ext` 内容。** 它不参与校验、不参与求值、不参与结算。
   要让某个东西参与，那就该是一个登记过的能力，而不是往 `ext` 里塞。
3. **任何一次写入都必须原样保留读到的未知键。** 保存、Patch 应用、布局重排、
   克隆都算写入。这一条有 round-trip 测试钉着（`src/skilltree/ext.test.ts`）。

### 3.2.3 属性表（能力 `attr/self`）

作者在文档里定义有哪些属性；用户填自己的值，宿主把值喂进 `attr.<key>` 事实
（§3.2.1），参与解锁条件 —— 「敏捷 ≥ 15」「阵营是守序」靠的就是它。

```jsonc
"attrs": [
  { "key": "str", "name": "力量", "type": "number", "min": 1, "max": 20, "default": 10 },
  { "key": "faction", "name": "阵营", "type": "enum",
    "options": [{ "value": "law", "name": "守序" }, { "value": "chaos", "name": "混沌" }] }
]
```

- `key`：`[a-z0-9_-]{1,32}`、树内唯一，条件里用 `attr.<key>` 读；
  `name`：显示名，把条件翻成人话、画输入框都靠它。
- `type`：`number`（可选 `min`/`max`）、`enum`（`options` 的 `value` 进事实、
  `name` 供显示）、`bool`。可选 `default`：用户没填时用它，没有 default 就是
  「不知道」（读它的条件不成立）。

两条要认清的口径：

- **值由用户自报，存在宿主一侧，不在文档里。** 每个 (用户, 树) 存一份。
  求值只认当前文档声明的属性，库里残留的旧键（作者后来删了那条属性）被忽略。
- **这是自评，不是防刷。** 用户能把自己的力量填成 20。要发真奖励的树若拿属性
  门控，得由宿主自己兜底，别指望运行时防作弊。

### 3.2.4 加点（能力 `rank/alloc`）

暗黑 / 魔兽那类天赋树：一个节点投 0..N 点，从一个点数池里花，投满才算完成。

```jsonc
"nodes": [ { "id": "fireball", "title": "火球", "x": 0, "y": 0, "maxRank": 5 } ],
"rules": { "points": 20, "pointsAttr": "lvl" }   // 点数池 = 固定 20 ＋ 属性 lvl 的值
```

- `maxRank`（缺省 1）：节点档位上限。缺省 1 时就是布尔节点（投 1 点＝完成），
  行为与不带这个字段的树逐位一致。
- 点数池：`rules.points`（固定）＋ `rules.pointsAttr` 那条属性的值。每投一点花池里一点。
- 派生事实：`tree.points`（池总量）/ `tree.used`（已投）/ `tree.free`（剩余）。
  **跨层投入要求**用条件读 `tree.used`，如「投满 3 点才解锁二层」写
  `gate.when: { "gte": [{ "get": "tree.used" }, 3] }`。
- 四态：投满 `done`；还能投且前置 / 条件 / 池都够 `open`；前置够但池空或条件不满足
  `blocked`；前置不够 `locked`。

**加点是沙盒**：投点不走完成结算那条路 —— 求值状态里的档位来自**方案**
（宿主存的一份分配），不来自完成记录。

### 3.2.5 成就的附加条件（能力 `cond/expr`）

成就（`awards[]`）除了「完成 `need` 个节点」，还能挂一条 `when`（同 §3.2.1 的写法），
两者都满足才算达成。

```jsonc
"awards": [ { "id": "aw1", "name": "力者", "need": 4,
              "when": { "gte": [{ "get": "attr.str" }, 15] } } ]
```

- 达成 ＝ `完成数 ≥ need` **且** `when` 成立。`when` 能读一切事实。
- **带 `when` 的成就不发奖励**（`when` 与 `gem` 互斥，`AWARD_COND_WITH_GEM`）：
  `when` 读得到用户自报的属性，再挂奖励就是「自报即印钞」。所以条件成就是纯认可；
  发奖励的成就仍按完成数结算 —— **结算路径不读事实**，它算成就跨线用的是
  无事实的档位状态，条件成就天然不会在那里产生发放事件。

## 3.3 校验：结构 ＋ 语义两段

**结构校验**管「字段类型对不对」（JSON Schema 那一层）。上限由宿主配置，不写死在
schema 里；这份实现的缺省是节点 ≤ 500、边 ≤ 2000、awards ≤ 16、attrs ≤ 32。

**语义校验**（结构合法后执行，`src/skilltree/validate.ts`）：

| 检查 | 级别 | 说明 |
| --- | --- | --- |
| 节点 id 格式合法、树内唯一 | error | |
| 边端点存在、无自环、无同向重复 | error | 编辑器已拦自环 / 重复，导入边界必须再拦 |
| **无环（DAG）** | error | 互为前置的节点永远 `locked`，是语义死锁 |
| `gate.need` > 入边数 | warning，**不改写文档** | 引擎求值本就取 min；改写会破坏 round-trip（作者写 `need=5` 打算后续补边，钳制入库后意图永久丢失） |
| `awards[].id` 唯一 | error | **顺序不做要求**：引擎按 `need` 求值，与顺序无关 |
| 属性表：`key` 格式与唯一、`type` 合法、number 的 `min ≤ max` | error | enum 没 `options` 是 warning（作者可能编到一半） |
| 条件引用了不存在的节点 / 未声明的属性 / 未知事实 | error | 悬空引用，界面上能直接指到是哪一条 |
| 用了已登记能力的门控字段但未声明 `requires` | error | 见 §3.6，防「静默错误求值」 |
| `requires` 含未知能力 | error | 本端不认识，别装作认识 |
| 全树消耗 > 全树产出 | warning | 有节点永远点不亮，但照样存得下 |
| 孤儿节点 | 合法 | 无前置即 `open`，是特性不是错误 |

校验结果三级：`error`（拒绝入库）/ `warning`（入库，告知，**不改写文档**）/ `info`。

## 3.4 Patch 协议 `skilltree-patch/1`

一次对文档的增量修改。它的用处不止一处：程序生成内容的写入口、版本 diff 的展示
格式、协作编辑的操作单元。

```jsonc
{
  "say": "把「和弦」拆成 3 步。",       // 给用户的一句话（可选）
  "set": { "meta": {}, "layout": "flow", "theme": {}, "res": {}, "rules": {}, "awards": [] },
  "drop": ["a7"],                        // 按 id 删节点（关联边级联删除）
  "dropEdges": [["a1", "a2"]],           // 删指定边
  "nodes": [],                           // 新增节点（replace 时为全量）
  "edges": [],                           // 新增边（replace 时为全量）
  "update": [ { "id": "a5", "gate": { "cost": 3 } } ],  // 按 id 部分更新既有节点
  "replace": false,                      // true = 整树替换
  "added": []                            // 本次新增节点 id，UI 高亮用，不参与语义
}
```

**应用顺序是规范定义的**：`drop → dropEdges → nodes/edges 新增 → update → set`。
先增后删是错的 ——「删旧节点 ＋ 新增同 id 节点」这个很自然的改法会互吞：
新增的先进去，紧接着被 `drop` 按 id 删掉，净效果是节点凭空消失。

**原子性**：应用后的文档必须通过 §3.3 全套语义校验，否则整个 Patch 拒绝，
原文档一点不动。

**坐标语义**：`replace` / 换布局 / 有 `drop` 才允许重排全图坐标；纯增量只摆新节点，
**不得冲掉手摆坐标**。

## 3.5 多实现与黄金测试集

规范要的是「谁都能自己实现一份引擎」，那就需要一个一致性锚点：`src/skilltree/fixtures`
下的黄金测试集，覆盖三个面：

1. **求值**：文档 ＋ 完成序列 → 期望四态 / 树内资源 / 等级 / 连带集合 / 结算事件；
2. **Patch 应用**：文档 ＋ Patch → 期望文档（含拒绝用例：同 id 新增、应用后成环）；
3. **校验器输出**：文档 → 期望 error / warning 列表。

这份 TypeScript 实现与 SkillsQuest 服务端的 Python 实现读同一批 fixtures，行为逐位
一致。任何第三方实现也该拿它们对齐自己：**改引擎先过 fixtures**。

涉及哈希互认的场合，规范化 JSON 采用 RFC 8785（JCS）—— 否则不同语言各自序列化
必然得出不同的 content hash。

## 3.6 演进机制：能力声明，而非版本大爆炸

- **minor 演进**：同一 major 内只做加法（新增可选字段）。老引擎按 L2 规则忽略并
  保留未知 `ext` 键。
- **能力声明 `requires`**：超出基线的特性必须声明。**每个能力登记它管哪些门控字段**，
  校验器强制双向绑定：命中门控路径的字段出现而 `requires` 未声明 → error
  `CAPABILITY_NOT_DECLARED`；声明了引擎不认识的能力 → error `CAPABILITY_UNKNOWN`。
  没有这条强制，L2 的「未知字段忽略保留」会让新特性在老引擎上**静默错误求值** ——
  一道门被当成不存在，而没有任何报错。

  已登记的能力（`src/skilltree/validate.ts` 的 `CAPABILITIES`，加一项就是往表里加一行
  ＋ 每个实现都实现它的求值）：

  | 能力 | 门控字段 | 说明 |
  | --- | --- | --- |
  | `cond/expr` | `nodes[].gate.when` / `awards[].when` | 可组合的条件，见 §3.2.1、§3.2.5 |
  | `state/checkin` | `rules.checkin` | 打卡树：同一节点每天可再来一次 |
  | `attr/self` | `attrs` | 属性表：作者定义属性、用户自报值，见 §3.2.3 |
  | `rank/alloc` | `nodes[].maxRank` / `rules.points` / `rules.pointsAttr` | 加点：档位上限与点数池，见 §3.2.4 |

- **major 边界**：收到不认识的 `spec` major（如 `skilltree/2`）报独立错误码
  `SPEC_UNSUPPORTED`，客户端据此区分「请升级」与「文档损坏」。
- **规划中的第一个新能力是公式参数化 `formulas`**：把 §3.2 里 v1 固定的树内
  reward / 能量 / 等级曲线开放成文档字段，缺省值即当前的硬编码值。
- **节点 id 稳定性**：作者工具做**弱检查**（新版本复用旧 id 但标题 / 类型大改时告警），
  不作为规范级 MUST ——「语义相同」不可机器判定，开放生态里也无法强制第三方遵守。
  进度跨版本的正确性由宿主的升级流程兜底。
